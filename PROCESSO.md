Iniciei o desenvolvimento analisando os requisitos do desafio. Em seguida, pedi ao Manus que interpretasse a proposta e transformasse os requisitos em um prompt técnico de desenvolvimento. Utilizei o Cursor para trabalhar a partir desse prompt. Escolhi esse fluxo porque queria compreender e conduzir a implementação, em vez de simplesmente receber um código pronto sem acompanhar as decisões.
A primeira versão da solução apresentou problemas tanto no deploy quanto nos testes. Embora a interface abrisse, a aplicação não conseguia transformar de forma confiável o conteúdo lido do PDF em uma estrutura útil para a tabela e para a persistência do resultado. A análise do código mostrou que a primeira abordagem achatava o texto extraído e não preservava adequadamente a relação espacial entre os itens do PDF. Como consequência, informações que pertenciam a linhas ou colunas diferentes podiam ser interpretadas como uma única sequência.
Para corrigir essa limitação, mudei a abordagem de extração para utilizar o pdfjs-dist. O código atual não apenas concatena o texto: a função textItemsToLayout usa as coordenadas x e y dos itens retornados pelo PDF.js para agrupar itens na mesma linha, ordenar os elementos horizontalmente e gerar caixas delimitadoras. Essa representação é usada pelo processamento genérico e fornece uma base melhor para a reconstrução de tabelas e para a associação entre texto e posição.
Essa mudança melhorou o resultado, mas não eliminou completamente a necessidade de revisão humana. Documentos com layouts variados, texto pouco estruturado ou informações ambíguas ainda podem produzir extrações incorretas. Por isso, a aplicação preserva os dados reconhecidos, calcula avisos de revisão e permite que o usuário compare a tabela com o PDF antes de salvar a versão corrigida.
Quando o PDF.js não encontra texto suficiente ou quando a extração especializada não consegue obter dados úteis, o pipeline utiliza um fallback de OCR. Nesse estágio, o Poppler renderiza a página em imagem e o Tesseract.js reconhece o texto em português. É importante registrar que a implementação atual do OCR não reconstrói as coordenadas dos textos: ela normaliza o texto reconhecido e o envia ao mesmo pipeline de extração. Uma melhoria futura seria utilizar uma saída de OCR com informações geométricas, como hOCR ou TSV, para reconstruir também a posição dos elementos. Essa melhoria ainda não está implementada no código atual.
Na etapa de implantação, inicialmente considerei utilizar apenas serviços gratuitos. Essa estratégia trouxe dificuldades de disponibilidade, limitações de terminal e problemas para manter simultaneamente a aplicação web e o worker. A solução final foi publicada em uma VPS usando Docker Compose e Coolify. O projeto utiliza um único código de aplicação, mas executa processos separados: o serviço app atende às requisições HTTP e o serviço worker processa os jobs em segundo plano. O MySQL e o serviço de migração são containers adicionais da mesma aplicação implantada.
O fluxo assíncrono funciona da seguinte forma: após o upload, a aplicação salva a transcrição e cria um job com status pendente no MySQL. O worker consulta a fila, faz o claim atômico do próximo job usando transação e SELECT ... FOR UPDATE, altera o status para processando e executa o processamento. Ao final, o job é marcado como concluido ou erro. O projeto possui atualmente uma instância fixa do worker; ele não cria novas instâncias automaticamente conforme a demanda. Em um ambiente de produção, seria necessário definir uma estratégia de escalabilidade, como múltiplas réplicas do worker, controle de concorrência e monitoramento da fila.

Os textos desta documentação foram produzidos a partir dos meus relatos, sendo posteriormente revisados e aprimorados com auxílio de inteligência artificial para melhorar a clareza, a organização e a precisão técnica. O conteúdo, as decisões e as responsabilidades pelo projeto permanecem de minha autoria o mesmo serve para solucao.md.
